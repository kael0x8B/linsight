# 接打电话告警时延修复与真实节点验证 · 2026-09-11

## 结论

接打电话链路的重复连续确认已收敛为一个职责：算法层只输出当前采样帧的 `phone_call` 候选，规则层独占 N/M、持续时间、冷却、恢复、去重和告警状态机。任务参数中的 `temporalN`、`temporalM`、`durationSeconds` 继续接受和保存，用于兼容现有任务与旧节点，但新 Runtime 不再用它们过滤行为候选。

配置页、算法包配置页和网关工作台会根据规则 AST 与 `sampleFps` 展示理论最短确认时延。新建或修改接打电话任务时，若下界超过 2 秒则前后端共同拒绝；已有超限任务可以继续启动和修改无关参数，只有变更规则版本或采样率时才要求满足新门槛。长时间停留、离岗等业务规则不套用接打电话的 2 秒门槛。

## 根因与计算口径

原链路先在 `CapabilityPostprocessor` 以任务参数执行一次 N/M + duration，再把通过后的对象交给 `RuleEngine` 执行规则中的第二次 N/M + duration。现场任务 32 原配置为 0.2 FPS，算法层 3/5 + 2 秒，规则层再次 3/5 + 2 秒，两个串联窗口使告警远晚于业务目标。

规则层的理论下界按采样边界计算：

```text
durationIntervals = ceil(durationSeconds × sampleFps)
minimumSeconds = (N - 1 + durationIntervals) / sampleFps
```

浮点计算对恰好落在采样边界的值消除微小舍入误差。原规则在 0.2 FPS 下，单独一层的下界已经是 `(3 - 1 + 1) / 0.2 = 15s`，因此无需等待现场报警即可判定配置与 2 秒目标明显冲突。该数字只是配置下界；解码、推理、排队、事件上传与页面渲染会继续增加真实时延。

## 兼容策略

- 任务 ID、规则 ID、Pipeline 和模型绑定不变；旧规则版本 73116 保留，新发布版本 73119 只把规则 `DURATION` 从 2 秒改为 0 秒。
- 旧任务启动不做追溯阻断。任务更新仅在采样率、规则 ID 或规则版本变化时执行 2 秒门禁；置信度、名称等无关修改仍可保存。
- Runtime 的平台重放和断电恢复不会被新门禁阻断；网关本地保存同样只在规则或采样率发生变化时阻断。
- 行为任务的旧时序字段仍在请求模型和数据库中。当前现场节点升级前用 `2/2/0` 通过旧 Runtime 的启动保护；升级后这些值不参与告警确认，可保留原值或改为 `1/1/0`，结果均由规则层决定。
- OCR 车牌多帧投票属于文本结果稳定机制，不是行为告警门槛，本次未移除。

## 真实节点观察与验收边界

2026-09-11 对节点 1「RK3566 现场边缘网关」进行了配置恢复和连续快照检查。任务 32 当前为 RUNNING，平台 configVersion 3，网关 revision/appliedRevision 均为 5，无错误；6 次读取的实际分析率为 1.025–1.036 FPS。处理总时延 P50 约 213–214 ms，P95 约 2.462–2.499 s；真实 `captureToResultP95Millis` 曾达到 3.987 s。配置目标 2 FPS 没有在该时段达到，因此不能把 1 秒配置下界写成现场端到端验收通过。

节点当前仍报告旧 Runtime `source-589817b12418`。在完成在线重部署前，现场任务使用 `2/2/0` 兼容值，旧算法层仍会增加一个短窗口；它用于保证任务不中断，不是“规则层唯一门槛”的最终节点证据。最终现场验收必须在节点版本升级后执行以下步骤：

1. 记录部署编号、Runtime 包 SHA256、节点 `agentVersion`、网关控制台 SHA256；确认 `runtimeStatus=UP`、48901 `/gateway-health` 为 UP，且节点心跳是部署后的新鲜心跳。
2. 对任务 32 停止、用 `artifacts/phone-call-latency-20260911/apply.py` 应用 `1/1/0` 兼容值并重启；确认平台与网关的 configVersion、revision、runId 一致，任务持续 RUNNING。
3. 用固定真人正例序列同时记录“动作首次在画面可见”的源时间戳、首个 `phone_call` 候选时间、规则 DETECTED/PENDING/ALARM 时间与页面可见时间。首帧候选应携带 `eventCandidate=true`、`temporalConfirmationOwner=RULE`，不应再出现算法层 `temporalConfirmed`。
4. 正例至少覆盖连续接听、短暂触耳、遮挡和多人；负例至少覆盖发信息、持物、摸耳、普通坐姿。按事件计算 P50/P95，不用单图、进程运行状态或配置公式代替真实效果。
5. 若实际分析率低于配置值，先处理 CPU 行为模型吞吐和并发模型争用。只有真实事件可见 P95 小于 2 秒、且误报/漏报达到现场验收口径，才能把算法效果从 PENDING 改为 PASS。

现有现场图片对遮挡人员仍漏检，且没有新的连续接打电话正例视频。本次修复解决的是重复门槛、配置可解释性和明显冲突阻断，不改变模型能力结论。
