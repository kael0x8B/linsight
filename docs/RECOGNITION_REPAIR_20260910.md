## 根因与修复

1. 原来运行的是任务 31「禁带区域手机出现」，只检测 COCO 手机物体；当时没有接打电话任务。这张截图中的手机也没有被通用模型检出。
2. 打架任务 28 的网关真实错误是 `MODEL_CAPACITY_EXCEEDED`：任务 29 使用旧 CPU 车辆模型 18，任务 31 使用 NPU 通用模型 121，合并车牌检测 71、OCR 23、行为模型 21 共需 5 个模型槽位，超过节点上限 4。
3. 平台拒绝接纳冲突后真实网关运行实例的 FAILED 心跳，后来尝试停止又遇到相同的旧修订号冲突，页面持续显示「网关配置已更新，正在同步」。`TaskServiceImpl.applyRuntimeReport` 现允许冲突失败状态下接纳已知运行实例的较新 FAILED 心跳，且支持用户已改为停止期望的恢复。保留节点、任务、配置版本、平台托管、严格递增修订号等约束。
4. 任务 29 停止后升级到 Pipeline 82664，车辆绑定改为 121；任务 28 升级到包 1.0.1 / Pipeline 82665，绑定 121+21。现有任务共享 121，合并模型仍为 4 个。未提高 2 GB 网关的模型容量。
5. 打架任务 28 配置连续确认规则 73015 / 73118：3/5 帧且持续 5 秒、冷却 60 秒。接打电话任务 32 使用 Pipeline 82666，绑定 121+21 和规则 73013 / 73116。两者 `validationOnly=true`、采样 0.2 FPS；接打电话还经过算法与规则两层连续确认，不能保证动作出现后 2 秒即告警。
