# ADR-0007：RK3566 NPU 加速与识别画面同步

- 状态：Accepted，负责人于本任务明确同意「接入 NPU 并完成同步验收」；执行与验收结果另行记录。
- 日期：2026-09-07
- 范围：Model、Node、Task、AI Runtime / Edge Agent、P06/P07。
- 沿用：模块化 Java 控制面、声明式 Runtime Manifest、现有 Pipeline/Rule、WebRTC 视频与独立 Canvas Overlay。

## 已验证的问题

现场摄像头 2 的子码流为 640×480；视频可流畅播放，但任务 2 串行执行人员与安全帽两个 ONNX 模型。
2026-09-07 10:53 的任务指标显示分析 0.542 FPS，处理耗时 P50 为 1756 ms，其中推理 P50 为
1572 ms。采样上限仍为 1 FPS。单纯提高采样配置不会突破计算吞吐。

当前主「AI 识别」画面是同一次分析的 JPEG 和目标框，保证图框配对，但只有约每 1.8 秒一张。
WebRTC 转发的 H.264 包与分析 FFmpeg JPEG 使用不同的时间路径；当前 Overlay timestamp 是
JPEG 到达 Runtime 的时间，不是经过关联的播放 PTS。直接把结果到达时刻当作视频帧时刻会导致框落后于人。

NPU 先前仅按 `/dev/rknpu` 判断，漏掉了现场的 DRM 接口。已实测：

- `/dev/dri/renderD129` 对应 `DRIVER=RKNPU`，Runtime 用户 linaro 有读写权限。
- 驱动 0.9.8、系统已有 librknnrt 2.3.2，内核 6.1.118；检查时 NPU 负载为 0%。
- 节点预装 MobileNet V1 在该 NPU 上连续运行 20 次成功，中位推理 5.755 ms。
  这只是硬件冒烟证据，不能外推为人员/安全帽模型或完整视频管线速度。
- 平台 ModelPool/Agent 当前只执行 CPU；发现硬件并不代表已经接通业务推理。

原始证据：`artifacts/helmet-realtime-diagnosis-20260907`。

## 拟议决策

### 1. 在现有 Runtime 模型池中增加 RKNN 执行后端

1. 使用已存在的 RKNN 制品格式与 ModelVersion 管理路线；不增加业务 Module 或独立推理服务。
2. 从现有人员/安全帽 ONNX 版本生成面向 RK3566 的 RKNN 版本，登记父制品 SHA256、转换工具版本、
   目标芯片、量化方式、校准样本清单及 Manifest。经过真实图片对比后才发布和切换任务绑定。
3. NPU 运行时复用节点已有驱动，不把刷系统、更新内核或重启网关作为此次接入的默认步骤。
   RKNN SDK 必须固定版本与哈希；独立转换环境不写入业务 Runtime 依赖。
4. `ModelPool`、任务模型查询键、Agent 部署持久化和重启恢复统一识别执行设备；移除当前 CPU 硬编码。
   不通过伪装为 ONNX/CPU 绕过格式、设备或模型版本校验。
5. 继续使用通用 Manifest 预处理和输出解码协议，不新建「安全帽专属后端」。安全帽仍通过 Person + PPE
   关联、跟踪和原 Rule 判断；unknown 不告警，实际头部框与置信度保留。
6. 未装载成功、设备不可用、芯片/制品不兼容均返回明确诊断；不静默回退 CPU 后仍标记 NPU。
   硬件发现、可执行后端、当前实际执行后端分别呈现。

### 2. 以视频时间轴完成同步显示

1. WebRTC 仍是视频主协议，Canvas 仍是独立图层。主画面回到连续视频；告警截图保留精确同帧证据。
2. 采样结果保留来自同一摄像头源的时间轴标识与 PTS，建立与浏览器播放帧的对应关系。
   先验证既有 aiortc H.264 转发与浏览器帧回调的时钟映射，再决定最小兼容字段扩展。
   不把不同进程的墙钟或消息收到时间当作相同 PTS。
3. 使用有界视频/结果缓冲，按正在展示的帧选择结果；过期、断流重连、任务 Run 切换清空关联。
   低延迟播放与严格图框对齐有取舍，缓冲时长应由实测决定并在界面说明。
4. 静态 ROI 始终按原视频坐标绘制。动态目标按带时间的真实检测/跟踪更新；如使用帧间跟踪，
   跟踪状态不得冒充一次新模型判断，不进入安全帽告警确认计数或伪造证据。
5. 仍保持同摄像头一个分析拉流/解码责任方，多任务订阅有界帧队列；不能为每个页面或能力重复解码。
6. 页面分别展示视频 FPS、AI 分析 FPS、结果年龄与运行后端。缺结果时正常视频继续播放，提示识别状态。

## 备选方案及取舍

| 方案 | 结论 |
| --- | --- |
| 只提高 sampleFps 或前端刷新率 | 计算已饱和，不能消除约 1.8 秒的模型处理耗时 |
| 持续把旧框叠在当前视频 | 可使视频流畅，但移动人物与框错位，不满足同步要求 |
| 用 JPEG 结果序列作为主画面 | 同帧证据可靠，但当前吞吐下不能满足流畅监控 |
| 直接更换更贵的节点 | 现有 NPU 已实机通过，先完成已有硬件的接入与测试，再判断是否需要升级 |
| NPU 加速 + 同源时间轴 + 有界同步 | 作为本 ADR 的拟议实现；实际速度与精度必须由人员/安全帽管线验收 |

## 交付与验收门槛

1. 原模型与 RKNN 模型在相同现场图片/连续视频上对比人员、头部框、PPE 状态、置信度及漏检/误检。
   先确认模型精度，再改变任务绑定；保留现场验证标识，不能把 SDK 示例分类成绩当业务验收。
2. 连续至少 5 分钟实测完整管线，分别记录解码、预处理、各模型推理、后处理、投递、播放与同步误差。
   第一阶段目标：视频不低于 20 FPS、分析不低于 5 FPS、采样到结果可用 P95 不超过 500 ms。
   这些是待验收目标，不是已取得的速度；若不能达到，明确报告真实瓶颈再选择下一步。
3. 用含移动、转头、遮挡、出画的现场片段验证框与画面的对应关系；静态 ROI 不漂移，结果不会跨 Run
   或重连时间轴叠加。同步偏差应可测量，目标不超过 100 ms；不能只凭一张静态截图验收。
4. 实测实时页、视频墙多会话、隐藏页签恢复和原图/带框截图；视频连续，资源可回收，控制面不代理逐帧视频。
5. 通过 Runtime 格式/设备/输出契约、Agent 幂等部署与重启恢复、Java 下发和前端时间对齐定向测试。
   新事件、证据校验、N/M 与持续时间规则继续通过；帧率调整必须沿任务配置版本和原规则单位生效。

## 兼容与回滚

- CPU/ONNX 模型版本、旧任务 Run 和事件不可变快照保留。RKNN 失败时停止该 Run，显式切回原绑定并新建 Run。
- 可选同步字段向后兼容；旧节点没有时间轴信息时展示明确状态，不宣称动态框已同步。
- 本次无数据库真值迁移；如实现需要新增模型执行元数据，按 ModelVersion 的版本化扩展前向兼容。
- 保留当前 Runtime 部署 27 和 Java 发布包，使用既有平台生命周期与回滚能力。

## 来源与确认边界

- [RKNN Toolkit2 官方说明](https://github.com/airockchip/rknn-toolkit2/blob/master/README.md)列出 RK3566/3568 与设备端 RKNN Runtime/Lite2 支持。
- [官方 YOLO11 示例](https://github.com/airockchip/rknn_model_zoo/blob/main/examples/yolo11/README.md)提供模型转换与部署路线；其基准不等于本项目完整管线成绩。
- 项目技能要求新增 inference backend 先有 ADR 和明确批准；负责人已确认本方案。
  NPU 探测修复和预装工具硬件冒烟本身不等于 LInsight 安全帽推理链路已经接通。

## 2026-09-08 扩展：入口主动刷脸的 NPU 后端

用户继续要求“为什么不使用 NPU，完成完整流程”。沿用本 ADR 的模型转换、固定执行契约和真实设备回执原则，增加 YuNet + SFace RKNN FP16 成对模型，解码器 `FACE_PAIR_SFACE_RKNN`，实际设备 `RKNPU`。模型包仍由 model 发布部署，入口短时会话由 task 管理，事件证据复用 event 和 MinIO；不修改普通连续视频任务语义。原 ArcFace 512 维参考模板不与 SFace 128 维混用。

实机版本 131 / 部署 23；登记、权限异常、授权通过、身份待核查的合成视频测试及资源边界详见 [入口主动刷脸实施说明](ENTRY_FACE_VERIFICATION_IMPLEMENTATION.md)。该扩展已验证 NPU 调用及软件链路，未将合成测试当作真人识别精度或活体验收。
