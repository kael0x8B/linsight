# 矿区车头车牌场景配置

车牌识别是通用视觉平台中的一个算法场景。任务创建、模型部署、事件中心和事件接口沿用平台通用模块；不把车牌字段或料仓字段固定到通用列表。

## 配置与使用

1. 在平台「算法中心」选择「厂区车辆识别 → 配置识别」，选择执行网关、摄像头及「厂区车辆车牌确认」规则；在盒子本地入口，通过「创建识别任务 → 识别算法 → 车牌识别」配置。
2. 选择本机已安装的中文车牌专用四角检测与配套中文车牌 OCR 模型，选择已有摄像头或填写 RTSP 地址。摄像头拍车头，识别区域框在目标车道的车牌可见范围。车牌任务不再要求车辆检测模型。
3. 本地模板保存为停止状态，在识别任务页检查参数并启用。平台场景默认 1 FPS（本地模板为 2 FPS）、OCR 置信度 0.75、最近 5 帧中至少 3 帧号码一致，投票最长保留 10 秒；默认离开恢复时间为 5 秒。场景验收状态保持 PENDING，需用现场样本验收。
4. 如需向业务系统提供事件，在盒子的通用「事件接口」中生成订阅密钥并启用 TCP 服务；业务客户端连接后可按车牌任务 ID 和 `VEHICLE_PLATE_RECOGNIZED` 类型订阅。
5. 通用「位置编号 / 位置名称」可填写料仓编号和名称（如 SILO-01 / 一号料仓），「摄像头」填写对应机位。无需增加平台专用料仓列。

## 场景结果

通用事件的 `data.result` 保留算法原始对象和属性。车牌场景使用以下属性：

```json
{
  "class": "license_plate",
  "attributes": {
    "plateNumber": "皖A12345",
    "plateConfidence": 0.95,
    "ocrStatus": "CONFIRMED",
    "displayLabel": "皖A12345"
  }
}
```

车牌号位于 `data.result.attributes.plateNumber`，时间位于 `data.occurredAt`，截图位于 `data.snapshot`，位置位于 `data.location.locationCode / locationName`，摄像头为 `data.cameraId / cameraName`。TCP 订阅协议见 [盒子事件接口](GATEWAY_EVENT_DELIVERY.md)。其他算法按同一协议传递自身结果。

缺少、非法或低置信度字符结果不能触发车牌事件；专用 OCR 同时检查整牌均值与最弱字符，两者均须达到 `ocrMinConfidence`（默认 0.75），弱字符返回 `LOW_CHAR_CONFIDENCE`。无效帧占用投票窗口，重复处理同一帧不增加票数。只有多帧确认的号码可以开始事件。

同车牌连续到访按稳定身份去重。已经确认的物理轨迹仍位于识别区时，短暂 OCR 失败只作为“目标仍在场”的观察，不关闭已有到访、不冒用旧号码作为新识别结果。跟踪丢失后重新确认同一号码，还须遵循规则 `dedup.windowSeconds` 的滑动去重窗口（当前预设 60 秒）；持续观察会延长窗口。真正离开后，恢复间隔用于关闭已有到访，去重窗口用于决定何时允许同号新事件。不同号码独立判断；缓存只在当前运行进程内保留，重启会重新确认。

平台事件列表和网关本地事件列表共用通用“识别结果”列，按事件快照显示算法结果；车牌事件显示 `plateNumber`，证据弹窗同时显示结果、任务和时间。该列也支持其他算法的结果标签或人数，不把平台改为车牌专用列表。历史事件展示其原始保存结果，不用当前识别结果覆盖。

## 算法与模型资产

「厂区车辆识别」是算法域的独立场景，编码 `yard-vehicle-recognition`，不是事件接口中的快捷按钮。模型资产在模型库独立登记并显示关联能力；车牌场景保持为通用平台中的可配置算法。当前流程仅执行车牌定位与 OCR；下表中的车辆检测模型是历史部署资产，不再参与车牌任务。

| 角色 | 模型资产 | 17 盒子版本 | 执行设备 |
| --- | --- | --- | --- |
| 车辆检测（历史资产，当前不使用） | 通用目标检测 · RK3566 NPU | 121 | RK3566 NPU |
| 车牌定位与四点信息 | 中文车牌检测 · 四角定位（专用 YOLO） | 138 | RK3566 NPU / RKNN |
| 车牌字符识别与颜色 | 中文车牌文字识别 · 专用 OCR（CNN/CTC） | 139（137 保留用于回退） | RK3566 NPU / RKNN FP16 |

2026-09-22 已完成 OCR 的 RK3566 FP16 适配，制品契约见
`runtime/model_assets/chinese-plate-ocr-rk3566-fp16-v1.json`。17 盒子 Runtime 升级至
`source-2fa2106ad7f8`，模型 139 部署 READY，并通过平台单图测试。沿用原始 ONNX 权重，未重新训练、未做 INT8 量化。
NPU 负责字符与颜色网络推理，原图裁剪、CTC 解码、最低字符置信度和多帧确认仍共用原处理逻辑。

同盒对比 149 张车牌裁剪，CPU/NPU 的文字和颜色逐张一致；138 张可读样本均为 127 张号码全对，
这表示适配没有改变该批文本结果，不代表 100% 识别准确率。一张正确车牌的分数跨过 0.75 门槛，详见报告。
OCR 单环节耗时中位数为 CPU 30.0 ms、NPU 8.8 ms；移动视频 126 帧回放的确认结果一致、
各产生一次内存中的到访告警，未保存或投递测试事件。含牌帧的完整处理耗时中位数为 309.2 → 289.7 ms，
不包含摄像头采集、视频解码和事件投递，不能把 OCR 的约 3.4 倍加速写成整体加速。

任务 33 仅将 `plate-ocr` 从 137 改为 139，保存为 revision 14 时保持停止；随后观察到启用的
revision 15，保留现场最新运行状态。CPU 137 的本地制品和历史版本均保留，但版本发布会将旧版本标为
SUPERSEDED，回退需显式恢复旧版本的可用发布状态并更新任务绑定，不会自动降级至 CPU。
没有向其他盒子部署；其他 RK3566 盒子需先升级兼容 Runtime、部署三个模型并通过本机测试。
复现数据、完整耗时口径及校验记录见 `artifacts/plate-ocr-npu-20260922/REPORT.md`。

版本、SHA256、参数、Pipeline 和规则定义保存在 `runtime/algorithm_presets/yard-vehicle-recognition.json`。通过已有领域 API 登记，无新增数据库或推理服务：

```bash
# 默认只检查车牌定位和 OCR 两个已发布且可执行的模型依赖；密码交互输入。
python3 scripts/publish-yard-vehicle-recognition.py
# 登记算法、发布编排与确认规则；重复执行复用相同记录。
python3 scripts/publish-yard-vehicle-recognition.py --publish
```

发布脚本不部署模型或启动摄像头。通过平台「配置识别」选择网关后，按既有部署流程安装所需模型并创建任务；删除过的旧任务不会恢复。当前预设只依赖车牌定位与 OCR；其他硬件需要选择兼容制品，不把 RKNN 当作通用 CPU 模型。

## 平台同步与现场验收

盒子新建的自治任务沿用本地事件归属。需要同时进入平台事件中心时，使用平台管理并下发的车牌任务。盒子 TCP 订阅、平台上传、平台 Webhook 独立配置和确认。

工程测试验证确认、去重、持久化和链路隔离。2026-09-20 已升级为专用模型，发布同一算法 72442 的 Pipeline 82668，并在 192.168.2.17 更新现有任务 33。真实单图、视频运行、页面及模型制品校验见 `artifacts/plate-specialist-20260920/REPORT.md`。未完成矿区车头正例视频及实际业务接收接口联调，不能宣称现场准确率通过。上线需用真实车头视频验证黄牌、蓝牌、新能源牌、夜间/逆光/灰尘、不同车距与短时遮挡，并核对重复率、事件延迟和断网补发。功能不推断载重、装料量，也不控制道闸或料仓设备。

同日升级前的 YuNet / LPRNet 组合在用户图片上失败：原图定位漏检，人工裁剪后的 OCR 输出非法 9 位字符，历史证据保留在 `artifacts/yard-vehicle-20260920/REPORT.md`。升级后的专用组合在 17 盒子上从同一 639×473 原图定位并透视裁出 46×16 车牌，输出 `粤BF27861`，单帧状态为 PENDING、确认事件数为 0。另追加的“场内”非标准测试牌出现省份字符误读；最弱字符约 0.583，虽整牌均值约 0.938，仍会被新门槛拒绝确认。该类版式尚未通过识别效果验收。


## 2026-09-20 专用模型升级（预训练权重）

场景预设 revision 2 使用独立模型 `chinese-plate-yolo` 与 `chinese-plate-ocr`。来源固定为
`we0091234/Chinese_license_plate_detection_recognition@670b765c09fff11850a7b1c542787ad66c24ae50`；
权重、许可证和预处理契约在 `runtime/model_assets/chinese-plate-specialist-v1.json` 登记。
使用已有预训练权重，没有重新训练。`scripts/export-chinese-plate-models.py` 从固定源码和权重导出 ONNX，
验证 PyTorch 与 ONNX 数值一致性；导出依赖在开发机隔离环境中，盒子仍使用已有 ONNX Runtime。

1. 对已升级 Runtime 的目标盒子登记模型：
   `python scripts/publish-yard-vehicle-recognition.py --models-only --model-artifacts <ONNX目录> --publish`。
2. 通过模型模块部署并在目标节点完成单图验证；模型执行状态 READY 后，使用
   `python scripts/publish-yard-vehicle-recognition.py --publish --update-existing` 发布新的场景 Pipeline。
3. 已有任务保持 ID、摄像头、规则、位置和接口绑定，只更新模型绑定、Pipeline 及新增参数。
   旧 Pipeline、旧模型保留，支持显式回退；旧场景不会自动迁移。

`plateUseRuleRoi=true` 将规则区域的外接矩形（含少量上下文）作为检测输入；车牌坐标和四角恢复到
完整原帧后进行透视矫正，OCR 输入保留原帧像素。实时链路直接传递内存中的 ROI 与 OCR 裁剪，
避免反复写盘和解码；文件测试入口仍使用无损 PNG。事件仍按原多边形判断。
车辆检测用于关联，不是车牌检测的前置通过条件；车辆漏检时仍能读取区域内车牌。
`plateMaxCandidates=10` 限制每帧 OCR 数量。双层车牌按检测分类分行拼接，异常角点退回检测框。

确认仍由同一目标的最近 5 帧、至少 3 个一致号码完成，最长 10 秒。无车牌帧、整牌或字符低分及非法号码
占用窗口；同一时间帧不重复计票，票数持平不确认。单图只能得到待确认号码，不能生成确认事件。
模型分数不能替代整牌正确率；静态图片、工程回归和现场连续视频的验收结果分别记录。

预览框也需要有效车牌证据：当前 OCR 通过号码格式、整牌和字符置信度校验后，显示待确认框，
多帧确认后再显示号码。时间叠字、残缺文字、低分新候选仍保留在诊断结果中，默认预览不画框。
已通过校验的同一轨迹短时 OCR 丢失时，最多保持 1 秒待确认框；无效帧不续期、不复用旧号码发事件。
明确不符合号牌格式的高分文字立即隐藏。该过滤不屏蔽画面的固定位置，也不提高车牌检测阈值。

当前事件格式校验接受普通中文 7/8 位号牌；模型的 78 字符表不代表所有特殊号牌或厂内自编号都已支持。
带“场内”等附加字样、特殊字体和不同编码规则，需要独立采样评估，不通过强改字符或放宽门槛伪造通过。
